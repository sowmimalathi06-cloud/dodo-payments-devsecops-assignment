# Task 3 — Service Mesh & Zero-Trust (Istio)

## Overview
Istio 1.22.5 was installed and `ledger-api` + its neighbour (`reporting`) were brought into
the mesh. Three layers of enforcement now sit in front of `ledger-api`, each catching a
different class of problem:

1. **mTLS (PeerAuthentication, STRICT)** — every connection between mesh workloads must
   present a valid Istio-issued certificate; plaintext traffic is refused outright.
2. **AuthorizationPolicy (default-deny + explicit allow)** — even *with* valid mTLS, only
   specific **workload identities** (SPIFFE / ServiceAccount) may call specific paths.
3. **Kubernetes NetworkPolicy (default-deny + explicit allow)** — an L3/L4 layer underneath
   both of the above, controlling which pods can even open a TCP connection in the first place.

**Note on Istio version:** the assessment's cluster runs Kubernetes 1.30.0. The latest Istio
(1.30.x at time of writing) requires Kubernetes 1.32+, confirmed by `istioctl x precheck`.
Rather than rebuild the cluster (which would have discarded all Task 1/2 work), Istio
**1.22.5** was used, the newest version still compatible with K8s 1.30 per Istio's support
matrix. This is flagged here rather than hidden.

## Setup

```bash
istioctl install --set profile=demo -y
kubectl label namespace payments istio-injection=enabled
kubectl rollout restart deployment ledger-api reporting -n payments
```

Both `ledger-api` (3 replicas) and `reporting` (1 replica) now run with **2/2** containers —
app container + `istio-proxy` Envoy sidecar — confirming mesh membership.

**Real issue hit and fixed along the way:** bringing `reporting` into the mesh triggered a
rollout that Kyverno correctly blocked, because `reporting`'s original manifest (from the
starter template) never had `securityContext.runAsNonRoot: true` — it had never been
hardened in Task 1 the way `ledger-api` was. Fixed by hardening `deploy/neighbour.yaml`
with the same securityContext pattern used for `ledger-api` (non-root, read-only fs,
dropped capabilities, dedicated ServiceAccount).

## 1. mTLS STRICT — enforced and proven

`deploy/istio/peer-authentication.yaml`:
```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: payments
spec:
  mtls:
    mode: STRICT
```

**Proof — plaintext request from outside the mesh is refused:**

A pod explicitly opted out of sidecar injection (`sidecar.istio.io/inject: "false"`) — a
genuine "outside the mesh" caller — attempted a plain HTTP request:

```
$ kubectl exec -n payments curl-test -- curl -v --max-time 5 http://ledger-api.payments.svc.cluster.local:8080/health
...
* Connected to ledger-api.payments.svc.cluster.local (10.96.151.58) port 8080
> GET /health HTTP/1.1
* Request completely sent off
* Recv failure: Connection reset by peer
curl: (56) Recv failure: Connection reset by peer
```

The connection was reset by `ledger-api`'s Envoy sidecar — it requires a valid mTLS client
certificate that this pod doesn't have.

## 2. Certificate issuance & rotation

Verified via `istioctl proxy-config secret`:
```
RESOURCE NAME   TYPE        STATUS   VALID CERT   NOT AFTER              NOT BEFORE
default         Cert Chain  ACTIVE   true         2026-07-29T10:16:50Z   2026-07-28T10:14:50Z
ROOTCA          CA          ACTIVE   true         2036-07-25T10:15:15Z   2026-07-28T10:15:15Z
```

**How it works:** `istiod` runs Istio's built-in Certificate Authority. Each sidecar's
`istio-agent` requests a workload certificate from `istiod` over the Istio CA's gRPC API,
authenticating the request with the pod's Kubernetes ServiceAccount token. `istiod` issues
a short-lived X.509 certificate (visible above: **24-hour validity**, `NOT BEFORE`→`NOT AFTER`
exactly 24h apart) with the workload's identity encoded as a SPIFFE URI
(`spiffe://cluster.local/ns/payments/sa/ledger-api`) in the certificate's SAN field.
The sidecar automatically requests a replacement before expiry — this is the rotation
mechanism, and it happens continuously with zero downtime and no manual intervention.
The **trust root** is the self-signed root CA generated by `istiod` at install time
(`ROOTCA`, valid 10 years) — every workload certificate in the mesh chains up to this
single root, which is what allows any two sidecars to mutually verify each other without
a shared external CA.

## 3. AuthorizationPolicy — default-deny + identity-based explicit allow

`deploy/istio/authorization-policy.yaml`:
```yaml
# Deny everything by default
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: default-deny-all
  namespace: payments
spec: {}
---
# Explicit allow, keyed on ServiceAccount identity (not IP)
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-ledger-api-authorized-callers
  namespace: payments
spec:
  selector:
    matchLabels:
      app: ledger-api
  action: ALLOW
  rules:
    - from:
        - source:
            principals:
              - "cluster.local/ns/payments/sa/reporting"
              - "cluster.local/ns/istio-system/sa/istio-ingressgateway-service-account"
      to:
        - operation:
            methods: ["GET", "POST"]
            paths: ["/health", "/tokenize", "/transactions", "/import", "/fetch"]
```

**Proof — authorized identity allowed, unauthorized identity blocked:**

Authorized caller (`reporting`'s own ServiceAccount, `cluster.local/ns/payments/sa/reporting`):
```
$ kubectl exec -n payments deploy/reporting -- curl -v ... /health
< HTTP/1.1 200 OK
{"status": "ok"}
```

Unauthorized caller (a pod using the `default` ServiceAccount — same namespace, same
network, but the **wrong identity**):
```
$ kubectl exec -n payments unauth-test -- curl -v ... /health
< HTTP/1.1 403 Forbidden
RBAC: access denied
```

Both pods were in the same namespace and network segment — the only difference was
ServiceAccount identity, confirmed cryptographically via each pod's mTLS certificate.
This is the core of zero-trust: **network location grants no trust; identity does.**

## 4. NetworkPolicy — defense-in-depth underneath

`deploy/istio/network-policy.yaml` adds a default-deny-ingress NetworkPolicy for the
`payments` namespace, with explicit allows for `reporting → ledger-api` on port 8080,
ingress-nginx → ledger-api, and istiod → all pods (required for cert issuance/config sync
to keep working).

**Verified compatible with the Istio layers above** — `reporting` still reaches `ledger-api`
successfully with all three policy layers active simultaneously.

## What each layer catches that the others don't

| Layer | Operates at | Catches | Does NOT catch |
|---|---|---|---|
| **NetworkPolicy** | L3/L4 (IP + port) | A pod on the wrong network segment trying to open a raw TCP connection at all — cheapest, earliest rejection point | Can't verify *who* is connecting, only *where from*. A compromised pod with the "right" IP/label still gets through. |
| **PeerAuthentication (mTLS)** | Transport (TLS) | Any caller without a valid Istio-issued certificate — e.g. a workload outside the mesh, or a raw non-mesh network scanner | Doesn't restrict *which* valid mesh identity can call — any workload in the mesh with STRICT mTLS enabled can still open the connection if not further restricted |
| **AuthorizationPolicy** | L7 (HTTP + identity) | The specific case NetworkPolicy and mTLS both miss: a *legitimate mesh workload* with a *valid certificate* but the *wrong identity/permission* for this specific service or endpoint | Doesn't stop traffic that never reaches this layer — relies on mTLS already being enforced beneath it for the identity claim to be trustworthy |

In short: NetworkPolicy is the cheap first filter, mTLS proves *a* valid identity exists,
and AuthorizationPolicy decides if *that specific* identity is allowed to do *that specific*
thing. Removing any one layer leaves a real gap the others don't cover.
